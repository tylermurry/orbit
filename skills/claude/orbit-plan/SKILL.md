---
name: orbit-plan
description: Convert supplied Orbit project scope, a GitHub issue, or completed interview decisions into a plan in Orbit, covering product capabilities, system capabilities, relationships and flows. Use /orbit-plan to create, revise, or review the plan.
disable-model-invocation: true
---

1. Call Orbit MCP `get_status`. Confirm the open contract and feature branch match the request. Call `get_plan` to see if a plan exists. If the Orbit MCP tools are unavailable, ask the user to open their project in Orbit and connect the Orbit MCP server.
2. Use the requested change, linked issue, existing spec, or interview decisions as the source of scope. Read referenced material. Assume discovery is complete. Ask a focused clarification only if a material ambiguity blocks faithful translation. Preserve scope, priorities, and sequencing from the source.
3. If asked to interview, use this exact instruction to guide the interview: “Interview me to find the real goal of this project. Bias toward small, compartmentalized specs. Make me verify key decisions explicitly so nothing is missed.” Use the confirmed decisions as the input.
4. Work out the full set of contract changes the scope implies. Read the contract at the chosen baseline (`list_entities`, `get_entity`, `list_flows`, `get_flow`) and decide, for each of these, what must be added, modified, or removed:
   - **Product capabilities** (kind `capability`): what people can do, with their behaviors.
   - **System capabilities** (kind `system`): the internal components that support them, with their behaviors. Do not stop at the product layer; new or changed product behavior usually needs a new, changed, or retired system.
   - **Relationships** between them (`dependsOn`, `uses`, `implementedBy`). Add the relationship first whenever a capability or flow step needs a link that does not exist yet, and remove links that no longer hold.
   - **Flows**: the ordered, step-by-step walk that explains how a capability works. Author one for each leaf capability worth explaining, update the flows whose sequence of calls changes, and remove flows for retired capabilities. Steps must reuse existing relationships (including ones added by this plan), use replies where a result comes back, and carry a short `label`.
   - **Tests**: use explicit IDs for new tests and map them to behaviors.
5. Summarize the proposed changes in those groups (product capabilities, system capabilities, relationships, flows, verification). For a new plan, use the contract at the chosen baseline, normally the current HEAD. Resolve and show the baseline commit before creating the plan. If the user specified another baseline, inspect that contract. Call `create_plan` with structured edit operations (`create_entity`, `update_entity`, `delete_entity`, `create_relationship`, `create_flow`, `update_flow`, `delete_flow`, and so on). For iteration, call `revise_plan` with the `fileHash` from `get_plan` (or from your last create/revise) and the delta from the current plan. The Plan view derives Planned from additions. Leave the actual contract and code untouched. Ask explicitly before replacing any plan. Pass the existing plan's `fileHash` and replace: true when the owner asks to replace it.
6. Call `view_changes` with `{"view":"plan","show":true}`. Summarize additions, modifications, removals, and potential impact for product capabilities, system capabilities, relationships and flows. If Orbit reports that the plan changed since you read it, read it again before revising. Preserve tickets as the implementation instructions.
